# Even G2 × Grok Bot 連携アプリ 仕様書

版: 0.1（アイデア・MVP設計）  
作成日: 2026年10月17日  
対象: 実装を担当するコーディングエージェント

## 1. 目的

Even G2から、ユーザーが普段使っているGrok BotのマスターBot一体に質問・依頼を送り、回答をグラス上で読めるようにする。既存Botの設定・記憶・利用可能なツールを活用することを目指す。

「GrokのモデルをAPIで呼ぶ独自チャット」を作ることとは異なる。既存のマスターBotに接続できなければ、目的を達成したとは扱わない。

## 2. 決定事項と設計上の仮定

| 項目 | 方針 | 位置付け |
| --- | --- | --- |
| デバイス | ユーザー所有のEven G2 | 確定 |
| 接続先 | ユーザーの既存マスターBot一体に固定 | 確定 |
| 起動方法 | G2のメニューから独自アプリを開く | MVP方針 |
| 音声による起動 | 「Hey Grok」の常時待ち受けは実装しない | 確定 |
| 質問入力 | 起動後にタッチ操作で録音し、音声を文字起こし | 提案。実機で操作を検証 |
| 出力 | 回答をG2にテキスト表示 | MVP方針 |
| 中継 | クラウド上のCloudflare Workers | 採用候補 |
| 保存 | Cloudflare D1 | 採用候補 |
| 利用者 | まずは本人一人 | MVP仮定 |
| スマートフォン | iPhoneとの連携を優先 | 開発時に機種・OSを確認 |

音声による起動を省くことと、アプリ起動後の音声入力を省くことは別。MVPでは後者を残す。

## 3. 最重要の未検証事項

### 3.1 既存マスターBotへの外部入力

既存の個人Botを指定し、外部アプリから依頼を渡せる公式の接続方法は未確定。GrokのモデルAPI、Grok AutomationsのWebhook、Grok Botのルーチンは別の機能として調査する。

公式資料にはGrok AutomationsのWebhook起動があるが、これだけでは既存マスターBotを起動できるとは判断しない。既存Botの指定、利用プラン、利用地域、会話の継続方法を実環境で確認する。

### 3.2 回答の取得

Webhookの受付成功とBotの回答完了を区別する。公式資料のWebhookは202 Acceptedで非同期受付する仕様で、HTTPレスポンスがそのまま回答になるわけではない。

回答の受け取り方は、公式の結果取得手段、イベント通知、またはBotから中継APIへ結果を投稿できるツール等を調査して決める。BotからのHTTP投稿も実行権限・通信制約を含めて検証する。

### 3.3 会話・記憶の継続

アプリ内のconversation_idとGrok Bot側の会話IDは同一ではない。追加質問が同じBotに届くことと、同じ会話の全文が引き継がれることを分けて検証する。Botの記憶を使うことも、毎回すべての過去会話が参照される保証とは異なる。

**この3点を先に検証し、接続経路を確定してからG2向けの本実装へ進むこと。架空のエンドポイントやBot ID指定方法を作らないこと。**

## 4. 想定するシステム構成

| コンポーネント | 責務 |
| --- | --- |
| G2向けEven Hubアプリ | 操作受付、マイク取得、録音状態・質問・回答の表示 |
| スマートフォンのEvenアプリ | G2と独自アプリを接続する実行基盤 |
| Workers API | 認証、リクエスト管理、文字起こしサービスとの接続、Botへの送信仲介、結果受信 |
| D1 | 質問、状態、回答、会話の対応関係の保存 |
| Bot接続アダプター | 検証済みの方法で既存マスターBotに依頼し、結果を対応付ける |
| 文字起こしサービス | 音声から日本語テキストへの変換。サービスは未選定 |

G2向けアプリは公式Even Hub SDKを使用する。中継にGPUは不要。Botの処理はGrok側で行い、WorkersでGrokモデル自体を動かさない。

### 通信の流れ（接続検証後の目標）

1. ユーザーが独自アプリを開き、タッチ操作で録音を開始する。
2. 録音終了後、音声を中継APIへ送り、文字起こしする。
3. 認識した文章を表示し、送信・録り直しを選べるようにする。
4. 送信時に中継APIがリクエストを保存し、マスターBotへの依頼を開始する。
5. G2側はrequest_idを使って処理状況を取得する。
6. Botの結果を中継側で受け取り、D1に保存する。
7. G2側が回答を表示する。長文はスクロールまたはページ送りする。

## 5. MVPの機能要件

### 5.1 入力と表示

- 日本語の質問・依頼を入力できる。
- 録音開始・終了、送信、録り直し、回答閲覧、追加質問に必要な最小操作を用意する。
- タップやスワイプの割当はSDKの実際のイベントと競合しない形で実機検証して確定する。
- 誤認識の確認画面を設ける。グラス上の文字編集はMVPでは不要。
- 録音の長さは初期値30秒を上限候補とし、音声の送信サイズと操作性を見て調整する。
- 画面には「録音中」「文字起こし中」「送信中」「処理中」「回答」「エラー」を区別して表示する。
- 回答本文は省略して消さず、ページ送り等で全文を読めるようにする。
- 通常の利用画面には認証情報・内部ID・スタックトレースを表示しない。

### 5.2 マスターBotとの接続

- 接続先はサーバー側で一体に固定し、クライアントから任意のBotを指定させない。
- Botの切替、作成、削除のUIは不要。
- 依頼と回答はrequest_idで対応付ける。
- 追加質問を同じ会話として渡せる場合は、その対応関係を保存する。
- 同じ会話に継続できない場合は、その制約を仕様に明記し、ユーザーに確認する。独自に既存会話と同等と扱わない。
- 承認が必要な処理は、自動承認せず、公式Grok Botアプリで確認するよう案内する。承認待ちを取得できない接続方式では、その限界を明示する。

### 5.3 非同期処理と障害時

- G2側は初期実装ではポーリングを利用する。目安は2秒間隔、長時間待機時は間隔を延ばす。
- 画面を閉じたり通信が切れたりしても、保存済みリクエストの状態を再取得できるようにする。
- 初期MVPは未完了の依頼を一件までに制限する。
- タイムアウトは回答待ちの期限を示す。Botの処理停止を意味しない。
- 待ち時間の目安は120秒とし、超過時も「状況を再確認」を選べるようにする。
- 処理が届いたか不明な場合、同じ依頼を自動で再送して二重実行しない。
- BotのキャンセルAPIが未確認のため、MVPで「処理停止」を保証しない。

## 6. 独自APIの案

以下は今回新規に作る中継APIの設計案であり、Grok側の公式APIではない。

| メソッド・パス | 用途 |
| --- | --- |
| POST /v1/transcriptions | 音声を受け取り文字起こし結果を返す |
| POST /v1/requests | 確認済みテキストを受け取り依頼を作成。202とrequest_idを返す |
| GET /v1/requests/{request_id} | 状態、回答、利用者向けエラーを返す |
| GET /v1/conversations/{conversation_id}/requests | 自分の会話の依頼と回答を取得する |
| POST /v1/bot-results | 検証でBotからの結果投稿を採用した場合のみ設ける |

依頼作成の入力例:

```json
{
  "conversation_id": "application-conversation-id",
  "client_request_id": "uuid-generated-on-client",
  "text": "明日の予定を確認して教えて"
}
```

状態取得の出力例:

```json
{
  "request_id": "server-generated-id",
  "status": "completed",
  "answer": "Botから取得した回答本文",
  "error": null
}
```

状態はaccepted / processing / awaiting_approval / completed / failed / delivery_unknownを候補とする。Bot側の通知がない状態を推測で表示しない。processingは観測可能な実行開始がある場合に用い、単に受付済みの場合はacceptedとする。待機期限は別フィールドで表現し、後から来た回答を保存できるようにする。

client_request_idは利用者単位で一意にし、重複送信時は既存のrequest_idを返す。これは中継での重複を防ぐものであり、外部Botの実行を完全に一回だけに保証するものではない。

## 7. データと認証

### 保存項目の候補

- conversations: id、owner_id、外部会話参照（取得可能な場合）、created_at
- requests: id、owner_id、conversation_id、client_request_id、text、status、answer、error_code、external_run_ref、created_at、updated_at
- callback_receipts: 外部通知ID、request_id、受信日時（結果通知の重複防止が必要な場合）

日時はUTCで保存する。初期の保存期間は30日を提案し、実装時に設定可能にする。録音データは文字起こし後に原則保持しない。会話履歴を消しても、Grok Bot側の履歴まで消えるとは扱わない。

### 認証方針

- GrokのパスワードやブラウザーCookieを独自アプリへ埋め込まない。
- 公式の接続・認証方式を優先する。認証方式未確定のままCookie流用等に進まない。
- Webhook署名鍵、文字起こしAPIキー等はWorkers Secretsに置く。
- クライアントは本人にひも付く失効可能な認証を使う。Grok側の鍵をクライアントへ渡さない。
- 一人用MVPでは端末ごとのランダムトークン方式を候補とし、配布・保存・失効方法を決める。アプリの公開ソースに固定トークンを書かない。
- 結果投稿を設ける場合は別の認証・署名を使用し、request_idだけで投稿を許可しない。
- 依頼の取得では所有者を必ず確認する。結果の重複・遅延・順不同到着を処理する。
- 本文やトークンを通常ログへ出さない。ログは処理ID、状態、所要時間、エラーコードを中心にする。

## 8. 技術選定の初期案

| 対象 | 候補 | 補足 |
| --- | --- | --- |
| G2向けアプリ | TypeScript、Vite、公式Even Hub SDK | Reactは必要に応じて採用 |
| 中継API | TypeScript、Cloudflare Workers | Honoは任意 |
| データベース | Cloudflare D1 | スキーマ変更はマイグレーション管理 |
| シークレット | Workers Secrets | 接続先ごとに分離 |
| 文字起こし | 日本語対応の外部音声認識API | 音声形式、料金、応答時間で選定 |
| Bot接続 | 調査後に選定 | 特定の未検証方式に固定しない |

SDKの音声形式を確認し、文字起こしサービスが要求する形式に変換する。変換コストや送信サイズがWorkersの制限に収まることを確認する。MVPではR2、Queues、Durable Objects、WebSocketは必要性が確認されるまで必須にしない。

## 9. 実装の順序と完了条件

### Phase 0: 接続可能性の検証（最優先）

1. 現在の公式資料と利用者のGrok Bot環境を確認する。
2. 既存マスターBotを指定して外部から一件のテキストを渡す。
3. Botが処理したことを確認し、その回答をプログラムで取得する。
4. 二件目の追加質問で会話の継続範囲を確認する。
5. 認証、必要プラン、接続方法、制約を短い検証報告にまとめる。

完了条件: 対象が既存マスターBotであること、回答を取得できること、追加質問の文脈の扱いを説明できること。

ここが未成立なら、本接続が完成したと報告しない。確認できた制約と代替案を提示する。モデルAPIでの代替や別Botの作成は目的の変更なので、ユーザーの合意を得る。

### Phase 1: 中継API

WorkersとD1を用意し、文字入力による依頼作成・状態取得・回答保存・認証・二重送信対策を実装する。まずPCから一往復できることを確認する。Botがすぐ完了するケースと、数分かかるケースを扱う。

### Phase 2: G2でのテキスト表示

Even Hubのシミュレーターと実機で、独自アプリの起動、固定テキストの依頼、処理状況表示、回答のページ送り、アプリを開き直した際の再取得を確認する。

### Phase 3: 音声入力

録音、文字起こし、認識結果の確認、送信、録り直し、追加質問を実装する。iPhoneとG2の実機でマイク権限、Bluetooth切断、アプリの前面・背面遷移を確認する。

### MVPの受け入れ条件

- G2で独自アプリを開き、日本語音声で質問できる。
- 既存のマスターBot一体が依頼を受け取り、その回答をG2で読める。
- 追加質問の会話継続範囲が検証結果と一致する。
- 長文の全文を読める。
- 通信切断後も保存済みの状態・回答を再取得できる。
- 同じ送信操作の重複で新規依頼を増やさない。
- 回答の遅延・失敗・承認待ちを、取得できる範囲で区別する。
- 秘密鍵が配布物とクライアントログに含まれない。

## 10. テストと納品物

状態管理、所有者チェック、重複送信、重複コールバック、遅延回答を重点的に検証する。Bot接続のモックはUI開発に使用してよいが、モックの成功を実Botとの接続成功として扱わない。

実装エージェントは、ソースコード、設定値の一覧（値は含めない）、D1マイグレーション、ローカル起動・デプロイ手順、Even Hubへの導入手順、接続検証報告、既知の制約を用意する。中継コードとBot接続処理を分離し、接続方式の変更時にG2 UIを作り直さずに済む構造にする。

## 11. MVP対象外

- 「Hey Grok」による音声起動・常時録音
- 複数Botの選択、Bot作成・削除
- G2からの画面共有や写真撮影
- 回答の音声読み上げ
- スマートフォンを介さない単独動作
- 一般公開向けの多人数アカウント管理
- 独自アプリからのGrok Botの承認操作

## 13. 実装エージェントへの開始指示

まずPhase 0を実施してください。最優先は、既存マスターBotへ外部から依頼を渡し、回答を取得する経路の成立です。未検証のAPI・認証・会話継続を推測で実装しないでください。接続が成立したら、Workers＋D1での文字入力の一往復、G2表示、音声入力の順で進めてください。必要なアカウント操作や設定が判明したら、利用者が行う手順と検証できた内容を具体的に示してください。
